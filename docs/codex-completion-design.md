# Codex の終了検知と TASK 結果判定の再設計

状態: 実装済み。2026-09-20。操作手順と実機確認範囲は [終了通知と自動完了](notifications.md) を参照。

## 現行実装の問題

旧 `lib/orca-result.cjs` はモデルに特定の文字列を回答させ、`lib/orca-execution.cjs` が端末出力から検索していた。この旧実装は削除し、Codex の通知プログラムに置き換えた。模擬 CLI のテスト成功だけでは実機からの通知配送を保証しないため、Windows と WSL 経由の実機試験も行った。

また、入力待ち・応答終了・プロセス終了のどれも、それだけでは TASK の完了条件達成を意味しない。追加質問をしたターンも終了する。対話 CLI は回答後も動き続ける。

## 採用方針

Orca のネイティブ Codex 対話を維持し、Codex の `notify` から実行先の TaskDesk 通知プログラムを起動する。モデルへの通知依頼、回答のマーカー、端末表示の文字列検索を終了検知の根拠から外す。

公式ドキュメントでは `notify` が `agent-turn-complete` を受け、JSON 引数に thread-id、turn-id、cwd、input-messages、last-assistant-message などが含まれる。ただし通知はターン終了を表し、成功ラベルではない。

1. TaskDesk の起動処理が実行先ユーザー専用の通知プログラムと実行専用ディレクトリを準備する。
2. 当該 Codex 起動だけに通知設定と実行識別情報を渡す。共有マシンの全体設定やユーザーの恒久設定は変更しない。既存の Orca / ユーザー通知設定は確認し、必要なら両方へ配送する。
3. Codex が通知プログラムを起動する。通知プログラムは JSON を検証し、一時ファイルからの rename でイベントを永続保存する。モデル自身によるファイル作成は要求しない。
4. TaskDesk が実行先から保存イベントを回収し、TASK・実行試行・Codex セッションとの対応を照合して受領を記録する。
5. 応答終了を記録した後、独立した結果判定を行う。検証結果が確定した場合だけ完了ラベルと後続実行を確定する。

## ローカル・SSH の配送

ローカルは実行先 OS のファイルを回収するアダプター、SSH は認証済み接続で実行先のイベントファイルを回収するアダプターを設ける。g15 の localhost は手元 PC の localhost ではないため、g15 から TaskDesk の localhost へ HTTP POST する設計にはしない。

Orca のホスト選択だけで TaskDesk が任意のリモートファイルを読めるとは仮定しない。実装前に Orca が提供するホスト別ファイルアクセスを確認する。利用できなければ、明示的に対応付けた SSH 接続または認証された専用配送経路が必要。Orca の公開されていない内部 API の存在を前提にしない。

実行前に同じ配送経路で通知プログラムの自己テストを行い、実行 ID の一致する受領応答を確認する。これは配送の検証であり、Codex 本体が通知を発火する検証とは分ける。未接続時は開始前に手動記録モードを明示する。

イベントは受領確認まで実行先に保持する。SSH 切断・PC スリープ・サーバー再起動後は未受領分から再開する。通知欠落や通信切断を成功として扱わない。

## 識別と重複防止

- TaskDesk の runId、nodeId、attemptId、実行先 hostId / worktree identity と、Codex の thread-id / turn-id を記録する。
- 初回通知は起動時に渡した実行専用の識別情報と送信記録を照合し、その後は同じ thread-id に固定する。cwd や「最新のセッション」だけで関連付けない。
- `(attemptId, threadId, turnId, eventType)` を一意キーにし、重複配送でラベルや後続実行を二重生成しない。
- ターン ID がない版はターンの正確な対応付けを別途確認するまで自動確定対象外とする。
- ユーザーが Orca で会話を続けた場合の各ターンを別々に記録する。古い検証結果で新しいターンの TASK を確定しない。判定確定前に後続ターン開始・進行中状態を照合できない場合は確認待ちにする。
- 通知プログラム、イベントファイル、受信 API は当該ユーザー／実行に限定する。実行識別用トークンはネットワーク認証の代わりにしない。

## 状態とラベル

実行状態と結果ラベルを別フィールドにする。

| 検知した内容 | 実行状態 | 結果・後続 |
| --- | --- | --- |
| Codex が応答終了 | 応答終了 → 検証中 | この段階では成功を付けない |
| 指定済みの完了条件を検証しすべて成功 | 完了 | 完了ラベル。承認必須なら承認後に後続へ |
| 成果物・テストが完了条件を満たさない | 終了 | 想定外結果。後続停止 |
| CLI / 検証処理の実行エラー | 失敗 | エラー。後続停止 |
| 質問・追加判断が必要、機械判定不能 | 確認待ち | 未確定。人が結果を記録 |
| 配送断・通知欠落・プロセスの予期しない終了 | 再接続待ち／中断 | 完了にしない |

検証は TASK に事前設定した検証コマンド、成果物条件などを実行先の同じワークツリーで評価する。AI の文章をそのままシェルコマンドとして実行しない。テスト成功だけで全要件を満たしたとみなさず、自動判定可能な完了条件を定義する。

自然言語の完了条件しかない TASK は、最終回答から判定案を作ることはできるが、推定と検証済み結果を区別する。判定不能は確認待ち。全 TASK を無条件に自動完了させることは保証しない。

## 代替案と適用範囲

- `codex app-server` は構造化された `turn/completed` などを取得できる。TaskDesk が対話・承認 UI を管理する構成に適する。ただし既存の Orca 内 Codex TUI のセッションを別の app-server でそのまま監視できるとは仮定しない。今回は対話経路を変えない notify 方式を第一候補にする。
- 非対話専用 TASK は `codex exec --json` と終了コードを監視できる。現在の Orca 上の対話 TASK を暗黙に非対話実行へ変更しない。
- Claude Code は別アダプターが必要。この Codex 向け通知設定で対応済みとは扱わない。

## 実装順と受け入れ条件

1. 対象ホストの Codex バージョン、起動時 notify 上書き、Orca 既存通知との共存、ファイル回収経路を検証する。手元で確認した CLI は 0.155.1。g15 での発火・配送は未検証。
2. 通知プログラム・永続キュー・回収アダプター・受領記録を実装する。
3. ターン終了と TASK 結果を分離した状態管理・検証・画面表示を実装する。
4. 新方式の実機検証後、マーカーによる自動確定を廃止する。起動済みの旧 TASK は手動記録で完了させる。
5. モデルへの特別な回答形式の指示なしで通常回答を取得できること、追加質問で完了にならないこと、SSH 切断からの回復、重複通知、別 TASK・古いターンの除外、再起動、CLI 異常終了、検証失敗、承認待ちを検証する。
